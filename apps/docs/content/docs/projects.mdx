Projects organize work that takes multiple [issues](/issues) to finish — a product launch, a migration, or a feature delivered in stages.

Work that a single issue can describe does not need a project. Projects fit a group of work that shares a goal, needs its progress tracked together, or needs shared repositories and working directories.

## Parts of a project

| Part | Purpose |
|---|---|
| **Name, icon, and description** | Goal, scope, and long-lived requirements; the description enters the execution context of agents working inside the project. |
| **Status** | `planned`, `in_progress`, `paused`, `completed`, or `cancelled`. |
| **Priority** | `urgent`, `high`, `medium`, `low`, or `none`. |
| **Lead** | A member or an agent — who coordinates the project. |
| **Start and target dates** | The project's planned time range. |
| **Issues and progress** | The work in the project and how much of it is finished. |
| **Resources** | Linked GitHub repositories or local directories on specific computers. |
| **Workflow** | The steps its issues follow and who takes over at each step. |

## Projects and issues

A project can contain any number of issues; an issue belongs to at most one project. Create issues directly inside the project, or pick or change the project from the issue's properties.

Project progress is computed automatically from linked issues:

```text
progress = issues in done or cancelled ÷ all issues in the project
```

`cancelled` means that work has been closed out of the project's scope, so it counts toward progress. Project status and issue status are independent: finishing every issue does not automatically set the project to `completed`, and changing the project's status does not bulk-change its issues.

## Project description and execution context

When an agent runs an issue inside a project, the project's name and description are added to that run's context. The description is the place for information every related issue needs: the goal, technical boundaries, delivery conventions. Requirements that apply to only one issue belong in that issue.

## Add resources

Project resources tell agents which code and working directories to use:

- **GitHub repositories**: provide a repo the runtime can check out, with an optional ref.
- **Local directories**: let the runtime on a specific computer work in an existing directory, whose contents the agent modifies directly.

See [Project resources](/project-resources) for how to choose and for the safety boundaries.

## Add skills

Skills attached to a project are delivered to every task in the project, in addition to the running agent's own skills. See [Attaching to a project](/skills#attaching-to-a-project).

## Add MCP servers

Workspace `owner`s and `admin`s can attach servers from the workspace MCP library (Settings → MCP) to a project, or run `multica project mcp add <project-id> --server-ids <server-id>`. Every task in the project then runs with them, alongside the running agent's own MCP servers:

- If the agent's own MCP configuration declares a server with the same name, the agent's entry wins.
- Each server has an audience: **All agents** (the default), only selected agents and agent labels, or all agents except selected ones. Change it from the server's row or with `multica project mcp audience`, and restrict servers whose credentials not every agent should hold.
- A server assigned to the agent but disabled stays off for that agent.
- An agent with no MCP configuration of its own switches to Multica-managed MCP for project runs, just as when a server is assigned to it directly.
- Agents cannot change project MCP servers, even when they run for an admin.

<Callout type="warning">
A project MCP server's configuration, including any token in it, is written onto every runtime that runs work in the project, including members' private runtimes. Attach only servers whose credentials everyone working in the project may hold.
</Callout>

## Choose a workflow

Choose the project’s **Workflow** to set its board columns and who takes over at each step. For example, development can go to one agent, review to another, and acceptance to a team member. Projects without another choice use **Default**: every status is available and nothing is handed off automatically. See [Workflows](/workflows) for setup and switching an existing project.

## Project lead

The lead can be a member or an agent and coordinates the project. A member who is the lead can also switch the project’s workflow. Making someone the lead does not assign every issue to them or start work automatically. A workflow step can hand issues to the project lead when you choose that option.

## Pin to the sidebar

A pinned project appears in your sidebar. Pinning is a personal preference and does not affect other members.

## Create, edit, and delete

Any workspace member can create and edit projects; only `owner` and `admin` can delete them.

<Callout type="warning">
Deleting a project does not delete its issues: they detach and stay in the workspace. The project's description, status, resources, skill attachments, and MCP server attachments are permanently deleted.
</Callout>
